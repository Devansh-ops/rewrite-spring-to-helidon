# Spring Framework 7 MVC versus Jakarta REST 3.1 response and binding semantics

**Status:** Design input for the v0.2 MVC and HTTP-response recipes
**Target:** Helidon MP 4.5.x, Jakarta REST 3.1, Jakarta Validation 3.0
**Scope:** media-type declarations, request parameters, request headers, cookies, status handling,
and `ResponseEntity` builder chains

## Conclusion

Most of the requested surface is automatable, but a safe recipe must distinguish three outcomes:

1. **Equivalent and automatic:** the source construct and target construct have the same relevant
   contract under checkable preconditions.
2. **Configurable:** OpenRewrite can generate a target implementation, but the desired error body,
   content-negotiation policy, decoding policy, or accepted status-level equivalence is an
   application decision.
3. **Refusal:** the source contains behavior that cannot be inferred or preserved locally. The
   canonical recipe must leave the complete controller unchanged and report the reason.

The most important boundaries are:

- Positive, constant `produces` and `consumes` declarations have direct Jakarta REST syntax. Their
  *selection behavior* is equivalent only when content negotiation, competing resource methods,
  and entity providers are also compatible.
- Spring MVC `@RequestParam` is not simply Jakarta REST `@QueryParam`: in Servlet MVC it can read
  query, form, and multipart parameters. The target annotation reads only the URI query.
- Spring applies a declared default to a missing **or empty** named value. Jakarta
  `@DefaultValue` applies only when the request metadata is absent. A blind annotation swap changes
  behavior.
- Spring request bindings are required by default. Jakarta REST parameter annotations do not
  express requiredness. `@NotNull` can preserve the missing-value **400 status** for reference
  parameters, but the response entity is not standardized.
- A whole Spring `HttpHeaders` parameter can be migrated only when every use is read-only and has
  an allowlisted Jakarta REST equivalent. In particular, Spring `getFirst` must not become Jakarta
  `getHeaderString`, which comma-joins multiple values.
- `@ResponseStatus` and `ResponseStatusException` do not have exact annotation/exception
  equivalents. Status-only cases can be generated under an explicit error-policy contract;
  reason-bearing cases use the Servlet error mechanism and require a chosen target error model.
- Many `ResponseEntity` chains can become `Response` chains. Relative `Location` values,
  Spring `ResponseCookie`, Spring `CacheControl`, generic entities, and status codes above 599 need
  special treatment or refusal.

Helidon MP 4 exposes Jakarta REST 3.1 and Jakarta Validation 3.0 as its portable REST and validation
programming models, so those specifications—not implementation accidents—are the canonical target
contract. Helidon 4 requires Java 21. See the
[Helidon MP specification matrix](https://helidon.io/docs/v4/mp/specifications) and
[Helidon MP introduction](https://helidon.io/docs/v4/mp/introduction).

## Decision vocabulary

| Decision | Meaning for the canonical recipe |
| --- | --- |
| Automatic | Rewrite only after all stated static preconditions pass; otherwise do nothing and report. |
| Configurable | Expose a separately named leaf recipe or option that states the accepted policy or behavior delta. Do not activate it silently in the canonical migration. |
| Refusal | Leave the controller as a Spring unit. A partial conversion can change routing, validation, or response precedence even if the remaining Spring annotation merely becomes inert. |

“Automatic” below means that the relevant source-level contract is preservable. It does not prove
that an arbitrary body has a target `MessageBodyReader` or `MessageBodyWriter`. Jakarta REST makes
entity conversion provider-dependent, and uses both the Java raw/generic type and media type when
selecting providers; see
[Jakarta REST sections 3.3.3 and 4.2](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#resource_method).

## `produces` and `consumes`

Spring `@RequestMapping` uses `produces` as a producible-media-type request condition, normally
matched against `Accept`, and `consumes` as a consumable-media-type condition matched against
`Content-Type`. Method-level declarations override type-level declarations. Both members accept
negated expressions prefixed with `!`; Spring content negotiation can also be configured with
strategies beyond the header. These rules are documented by
[`@RequestMapping.produces`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/bind/annotation/RequestMapping.html#produces()) and
[`@RequestMapping.consumes`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/bind/annotation/RequestMapping.html#consumes()).

Jakarta REST uses `@Produces` and `@Consumes`. Method declarations likewise override class
declarations, and absence means `*/*`. If `Accept` is absent, the client is treated as accepting
`*/*`; if `Content-Type` is absent, `*/*` is used for **method matching**, while an eventual entity
reader sees `application/octet-stream`. A selection failure produces 406 or 415 as appropriate.
Jakarta REST also defines client `q` and server `qs` preference handling. These rules are normative
in [sections 3.5, 3.7, and 4.2](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#declaring_method_capabilities).

### Safe mapping

| Source | Target | Decision | Preconditions |
| --- | --- | --- | --- |
| One or more positive compile-time media-type strings | `@Produces({...})` / `@Consumes({...})` | Automatic syntax mapping | No value begins with `!`; every constant value is resolved; method/type override is retained; the complete controller is migrated atomically. |
| Spring `MediaType.*_VALUE` annotation constant | Its resolved string literal, or the exact Jakarta constant when one exists | Automatic | Resolve the constant value rather than assuming similarly named fields have the same catalog. |
| Wildcards or media-type parameters | Same literal | Configurable equivalence | Only after differential tests prove matching and provider selection for the endpoint set. `qs` has target-defined meaning and must not be invented. |
| A negated Spring expression such as `!text/plain` | None | Refusal | Jakarta `@Produces` and `@Consumes` have no exclusion syntax. Expanding a complement is not stable as providers and media types change. |
| Custom/composed request-mapping annotation | Potentially a generated Jakarta annotation set | Refusal in v0.2 | Spring meta-annotation, aliasing, and mapping-combination rules need a separate structural recipe. |

Even all-positive literals are not, by themselves, proof of wire equivalence. The recipe should
claim full equivalence only when there is no competing same-path/method resource whose selection can
change, the source uses header-based negotiation, and the target module provides readers/writers
for the same entity and media types. Otherwise the syntax conversion is safe but activation belongs
behind a documented compatibility option and runtime contract tests.

## Named request values

### Cross-cutting default and required semantics

Spring's `@RequestParam`, `@RequestHeader`, and `@CookieValue` all default `required` to `true`.
Declaring `defaultValue` implicitly makes them optional. Spring's common named-value resolver applies
the default when the resolved value is absent **and when it equals the empty string**; it can also
resolve `${...}` placeholders and `#{...}` expressions before conversion. See the
[Spring annotation APIs](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/bind/annotation/RequestParam.html) and the
[resolver implementation](https://github.com/spring-projects/spring-framework/blob/7.0.x/spring-web/src/main/java/org/springframework/web/method/annotation/AbstractNamedValueMethodArgumentResolver.java).

Jakarta REST `@DefaultValue` applies when the corresponding request metadata is **not present**. With
no default, a missing value becomes an empty `List`, `Set`, or `SortedSet`, `null` for another
reference type, or Java's default value for a primitive. This is the contract of
[`@DefaultValue`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/defaultvalue).
The parameter annotations have no `required` member.

Consequences:

- `defaultValue = "x"` must not become only `@DefaultValue("x")`: an explicitly empty input would
  remain empty at the target instead of becoming `"x"`.
- A literal default on a `String` can be preserved by injecting the nullable raw value, creating a
  collision-free local value with `raw == null || raw.isEmpty() ? default : raw`, and rewriting all
  uses to that local. This is **automatic only** when data-flow analysis proves that the parameter
  does not escape in a way the rewrite cannot update and the new local preserves effective-final
  use in lambdas and inner classes.
- Typed defaults are not a local normalization problem. Target conversion can fail before the
  resource method runs, especially for an empty value. Preserve them only with a dedicated
  `ParamConverter`/raw-string conversion policy that reproduces Spring's configured conversion
  service; otherwise refuse.
- Placeholder or expression defaults need a separate Spring configuration/expression migration.
  They must not be copied into `@DefaultValue` as literal text.
- For reference parameters, adding `jakarta.validation.constraints.NotNull` can make a missing
  required value a 400 response. Jakarta REST specifies 400 for a resource-parameter constraint
  violation, but does not standardize the response entity. This is therefore a configurable
  **status-equivalent** mapping, not exact wire equivalence; see
  [Jakarta REST section 7.6](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#validation_error_reporting).
- A primitive target cannot distinguish “missing” from an explicitly supplied Java-default value.
  Reboxing it and adding `@NotNull` changes the Java method signature and may affect direct callers
  and overrides. Refuse unless a whole-program signature recipe proves that change safe.
- Spring's conversion service and Jakarta REST's constructor/`valueOf`/`fromString`/
  `ParamConverter` rules are different extension points. Attributed types and an inventory of
  custom converters are prerequisites for typed-parameter conversion. The target conversion rules
  and failure statuses are specified in
  [Jakarta REST section 3.2](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#resource_field).

### `@RequestParam`

In Spring Servlet MVC, request parameters include query parameters, form data, and multipart data
because the binding is based on the Servlet request parameter map. Spring documents this explicitly
in
[`@RequestParam`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/bind/annotation/RequestParam.html).
Jakarta `@QueryParam` extracts only a URI query parameter; form and multipart parts have distinct
target models, as defined by
[`@QueryParam`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/queryparam) and
[Jakarta REST section 3.3.2](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#resource_method_parameters).

| Spring shape | Decision | Reason or generated target |
| --- | --- | --- |
| Optional reference `String`, no default | Configurable | Map to `@QueryParam` only under an explicit **query-only endpoint contract**. HTTP method alone is evidence, not proof, that form or multipart values are irrelevant. |
| Required reference `String`, no default | Configurable | Query-only contract plus `@QueryParam` and `@NotNull`; preserves missing-value 400 status, not error body. |
| Literal-default `String` | Configurable/automatic leaf | Query-only contract plus raw injection and missing-or-empty local normalization. |
| `Map`/`MultiValueMap` without a name | Refusal | Spring binds all request parameters across its Servlet parameter sources. Jakarta has no equivalent single query annotation, and a URI-only map would narrow the contract. |
| Numeric, enum, date, or custom type | Refusal by default | Spring conversion and Jakarta conversion can differ. Target query conversion failure is normally a 404 with no entity, while Spring MVC normally treats argument conversion as a 400. A selected `ParamConverter`/exception policy can make this configurable. |
| Primitive, `Optional<T>`, custom collection, form/multipart-capable endpoint | Refusal in the canonical recipe | Missing values, supported container types, and/or parameter source differ. |

For a Jakarta scalar parameter with repeated values, `@QueryParam` uses the first value in lexical
order; collection and array targets retain multiple converted values. A recipe must therefore
preserve the parameter shape and test repeated values, not silently collapse a Spring collection to
a scalar. The target behavior is stated in the
[`@QueryParam` API](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/queryparam).

### `@RequestHeader`

Named Spring request headers have the same required/default concerns. Spring resolves all values of
a named header and passes them through `WebDataBinder` conversion; missing required headers raise a
Spring missing-header exception. See the
[Spring request-header resolver](https://github.com/spring-projects/spring-framework/blob/7.0.x/spring-web/src/main/java/org/springframework/web/method/annotation/RequestHeaderMethodArgumentResolver.java).
Jakarta `@HeaderParam` supports its own conversion rules and, for a scalar receiving multiple header
values, uses the first value in lexical order; header names are case-insensitive. See
[`@HeaderParam`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/headerparam).

The safe matrix is therefore:

- Optional reference `String` with no default: automatic only under a declared single-valued-header
  contract; otherwise configurable and tested with repeated lines.
- Required reference `String`: configurable status-equivalent mapping with `@NotNull`.
- Literal-default `String`: generated missing-or-empty normalization, subject to the same data-flow
  rules as request parameters.
- Collections/arrays: require an exact supported target collection shape and differential ordering
  tests.
- Typed or custom converted headers: require converter compatibility. Although both frameworks tend
  to report 400 on header-conversion failure, the conversion algorithm and body still differ.

### `@CookieValue`

Spring `@CookieValue` can inject a scalar or `jakarta.servlet.http.Cookie`. Its Servlet resolver
URL-decodes scalar cookie values by default and has a configuration switch to disable that
behavior. See
[`@CookieValue`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/bind/annotation/CookieValue.html) and the
[Servlet cookie resolver source](https://github.com/spring-projects/spring-framework/blob/7.0.x/spring-webmvc/src/main/java/org/springframework/web/servlet/mvc/method/annotation/ServletCookieValueMethodArgumentResolver.java).
Jakarta `@CookieParam` defines cookie extraction and conversion but does not specify Spring's scalar
URL-decoding step; it can inject `jakarta.ws.rs.core.Cookie`, which is not the Servlet cookie type.
See [`@CookieParam`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/cookieparam).

Accordingly:

- An optional `String` cookie is configurable, not universally automatic. The user must select
  either a proven no-decode source configuration or a generated decoder that exactly matches the
  source configuration. Do not substitute `java.net.URLDecoder`; its `+` handling is not proof of
  Spring URI decoding semantics.
- Required and defaulted cookies additionally need the `@NotNull` or missing-or-empty policies
  described above.
- Servlet `Cookie` to Jakarta REST `Cookie` is a structural migration. Permit only an allowlist of
  read operations with proven equivalents; refuse mutation, escape to Servlet-typed APIs, or
  unknown methods.
- Typed cookies need conversion and decoding compatibility. Jakarta REST specifies 400 for ordinary
  header/cookie conversion failures, but that does not prove the same converter or error entity.

## Whole-request `HttpHeaders` injection

Spring permits `@RequestHeader` on `HttpHeaders`, `Map`, or `MultiValueMap` without a name to receive
all headers. Jakarta REST permits `@Context jakarta.ws.rs.core.HttpHeaders` on a resource method
parameter in version 3.1. The target map is read-only and case-insensitive. See
[`@RequestHeader`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/bind/annotation/RequestHeader.html),
[`jakarta.ws.rs.core.HttpHeaders`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/httpheaders), and
[Jakarta REST section 10.2.3](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#context_headers).

The v0.2 recipe can safely transform the parameter type and annotation only after analyzing every
use. An allowlist can include:

| Spring use | Jakarta target | Notes |
| --- | --- | --- |
| `headers.getFirst(name)` | `headers.getRequestHeaders().getFirst(name)` | Do **not** use `getHeaderString`; that concatenates all values with commas. |
| `headers.get(name)` | `headers.getRequestHeader(name)` | Preserve nullable/list behavior and the declared list type. |
| `headers.containsHeader(name)` | `headers.getRequestHeaders().containsKey(name)` | Both header maps are case-insensitive by contract; test the Helidon runtime. |
| `headers.headerSet()` / header-name iteration | `headers.getRequestHeaders().entrySet()` or `keySet()` | Rewrite the surrounding type from Spring's entry view to the Jakarta multivalued map view. |
| `headers.getAccept()` | `headers.getAcceptableMediaTypes()` | Also rewrite Spring `MediaType` consumers to Jakarta `MediaType`; ordering is content-negotiation ordering. |
| `headers.getContentType()` | `headers.getMediaType()` | Preserve nullable behavior. |

Refuse the entire controller when the Spring object is mutated, stored, returned, passed to an
unmigrated method, compared by concrete type, or used through an accessor without a proven target.
The Jakarta request map is read-only, so even a mutation that affected only Spring's local copy can
throw at the target. Although Jakarta REST 3.1 supports `@Context`, its specification announces that
a future API version intends to move injection toward CDI; the generated code is nevertheless valid
for the pinned Helidon MP/Jakarta REST 3.1 target. See the
[Jakarta REST 3.1 `@Context` compatibility note](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#context-injection).

## Status annotations and exceptions

### `@ResponseStatus`

Spring `@ResponseStatus` can annotate a method or exception class. On a handler method it sets the
response status unless a `ResponseEntity`/other status-setting return value takes precedence. A
non-empty `reason`, and exception-class use, are handled through the Servlet error mechanism; Spring
warns that the response is then considered complete and commonly receives a container-generated
HTML error page. Class-level status is inherited unless a method overrides it. These rules are in
[`@ResponseStatus`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/bind/annotation/ResponseStatus.html).

Jakarta REST has no corresponding status annotation. A resource method can return a `Response`, and
an exception can be handled by an `ExceptionMapper`; their contracts are in
[Jakarta REST sections 3.3.3, 3.3.4, and 4.4](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#resource_method).

| Source case | Decision | Target strategy and boundary |
| --- | --- | --- |
| Method annotation, empty reason, method already converted to return `Response` | Automatic | Set the same known 100–599 status while preserving entity and metadata. If a `ResponseEntity` branch supplies a status, retain its precedence. |
| Method annotation, empty reason, plain/`void` return | Configurable structural rewrite | Change all returns to `Response.status(code).entity(body).build()` or status-only `build()`. Require no incompatible override/direct caller, and preserve generic entity metadata. |
| Type-level annotation, empty reason | Configurable scanning rewrite | Materialize the effective status on every resource method, respecting method overrides and response-return precedence. Convert the class atomically. |
| Any non-empty reason | Refusal without an error policy | A Jakarta response reason phrase or exception message does not reproduce Servlet `sendError` and its container body. |
| Exception class annotation | Configurable generated `ExceptionMapper` for status/headers only | Exact entity, content type, reason localization, and logging require an explicit error schema. Refuse by default. |

### `ResponseStatusException`

`ResponseStatusException` carries a status, optional reason/cause, `ProblemDetail`-based error
metadata, and response headers. Spring MVC's resolver applies the exception headers and invokes
`sendError` with the status and optional reason. See
[`ResponseStatusException`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/server/ResponseStatusException.html) and
[`ResponseStatusExceptionResolver`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/web/servlet/mvc/annotation/ResponseStatusExceptionResolver.html).

Jakarta `WebApplicationException` can carry a `Response`, and an `ExceptionMapper` can create one,
but an exception message is not a standardized HTTP entity. See
[`WebApplicationException`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/webapplicationexception) and
[`ExceptionMapper`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/ext/exceptionmapper).

Therefore only a separately selected **status-and-headers policy** should rewrite direct,
status-only `ResponseStatusException` construction to a `WebApplicationException` containing a
target `Response`. It must copy statically understood headers and accept that the target error body
is controlled by the selected policy. Refuse a reason, localized detail, subclass, overridden
`getHeaders`, unresolved/dynamic status, or any code that catches or inspects the Spring exception.
Preserving a cause for diagnostics still does not preserve the response entity or container logging.

## `ResponseEntity` builder chains

Spring `ResponseEntity` represents status, headers, and an optional body. Its builders support
arbitrary headers, location, cache control, content type, and status factories. Jakarta
`Response.ResponseBuilder` supplies corresponding low-level operations: `status`, `entity`,
`header`, `type`, `location`, `cookie`, and `cacheControl`. See the
[Spring builder APIs](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/http/ResponseEntity.HeadersBuilder.html) and
[`Response.ResponseBuilder`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/response.responsebuilder).

Before any chain rewrite, require that the value is a server resource return, not a Spring HTTP
client value; that no builder escapes; that every chain operation is understood; and that all return
branches in the controller can be converted atomically.

### Factories, body, and status

| Spring form | Jakarta form | Decision |
| --- | --- | --- |
| `ResponseEntity.ok().build()` | `Response.ok().build()` | Automatic |
| `ResponseEntity.ok(body)` | `Response.ok(entity).build()` | Automatic for a non-generic entity with a proven writer; otherwise preserve generic type as below. |
| `accepted()`, `noContent()`, `badRequest()`, `notFound()`, `internalServerError()` plus `build()` | Corresponding known status builder | Automatic after resolving the status to a 100–599 integer. A target convenience factory is optional; explicit `Response.status(...)` is easier to audit. |
| `status(HttpStatus.CONSTANT)` or literal 100–599 | `Response.status(code)` | Automatic |
| Dynamic `HttpStatusCode` / integer | None by default | Refuse unless range analysis proves 100–599. Spring `HttpStatusCode` accepts any positive three-digit code, while Jakarta `Response.status(int)` rejects values outside 100–599. |
| Known 600–999 status | None | Refusal; preserving it needs a non-portable server API. |

The status-range difference follows from
[`HttpStatusCode`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/http/HttpStatusCode.html) and
[`Response.status(int)`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/response#status(int)).

Jakarta REST uses the response entity's raw and generic types to select a writer. When a Spring
method returns a parameterized body through `ResponseEntity`, erasure can change writer selection
after conversion to `Response`. The target builder API makes the caller responsible for supplying a
`GenericEntity` when generic metadata is needed. Generate an attributed wrapper such as
`new GenericEntity<List<Item>>(body) {}` only when the exact generic type is known; refuse raw,
wildcard, captured, or unresolved types. See
[`ResponseBuilder.entity`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/response.responsebuilder#entity(java.lang.Object)) and
[Jakarta REST section 3.3.3](https://jakarta.ee/specifications/restful-ws/3.1/jakarta-restful-ws-spec-3.1.html#resource_method_return).

### Arbitrary headers

Spring `header(name, values...)` adds all supplied values. Jakarta `header(name, value)` adds one
value, while a `null` value removes all existing values of that name. A safe recipe can unroll a
statically known, non-null Spring vararg list into target calls in source order. Dynamic arrays,
possibly-null values, or a name whose evaluation has side effects need temporaries or refusal so the
rewrite does not alter evaluation count/order. Both behaviors are documented by the
[Spring `HeadersBuilder.header` API](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/http/ResponseEntity.HeadersBuilder.html#header(java.lang.String,java.lang.String...)) and
[Jakarta `ResponseBuilder.header` API](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/response.responsebuilder#header(java.lang.String,java.lang.Object)).

Spring `.headers(HttpHeaders)` copies a multivalue structure, and `.headers(Consumer<HttpHeaders>)`
permits arbitrary live mutation. These are not annotation substitutions. Refuse them in the
canonical v0.2 recipe unless a separate structural visitor can prove every header value, mutation,
and evaluation-order effect. A raw `Set-Cookie` header is still an ordinary multivalue header and
may be preserved as such when the string expressions remain available without Spring types.

### Content type

`BodyBuilder.contentType(Spring MediaType)` can become target `.type(Jakarta MediaType)` or
`.type(String)`. This is automatic for a resolved constant or a structurally converted target
media-type value. Refuse unresolved expressions, mutable Spring media-type objects, or parameters
whose target body writer is unavailable. The source and target operations are defined by
[`BodyBuilder.contentType`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/http/ResponseEntity.BodyBuilder.html#contentType(org.springframework.http.MediaType)) and
[`ResponseBuilder.type`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/response.responsebuilder#type(java.lang.String)).

### `Location`

Spring `.location(uri)` sets the `Location` header to the supplied URI, and `created(uri)` combines
that header with 201. Jakarta `.location(uri)` resolves a relative URI against the application base
URI. A blind chain rename therefore changes a relative `Location`. See
[`HeadersBuilder.location`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/http/ResponseEntity.HeadersBuilder.html#location(java.net.URI)) and
[`ResponseBuilder.location`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/response.responsebuilder#location(java.net.URI)).

- A URI proven absolute may use target `.location(uri)`.
- A possibly relative URI should use explicit status 201 where appropriate plus a raw `Location`
  header, avoiding the target resolver. Header serialization of the URI must be covered by the
  pinned Helidon runtime contract test; if exact wire text is required, generate the proven string
  representation once without changing evaluation order.
- An unresolved URI whose absolute/relative behavior cannot be preserved is a refusal, not a reason
  to call target `created(uri)`.

### Response cookies

Spring response cookies normally enter a `ResponseEntity` through `Set-Cookie` headers built from
`ResponseCookie`. Spring's model supports path, domain, `Duration` max-age, secure, HTTP-only,
free-form SameSite, and Partitioned. Jakarta `NewCookie` supports a related but non-identical model,
including integer max-age and a fixed `SameSite` enum, and has no Partitioned member. See
[`ResponseCookie`](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/http/ResponseCookie.html) and
[`NewCookie`](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/newcookie).

Safe outcomes are:

- Preserve an already-formed, Spring-independent `Set-Cookie` string with target `.header(...)`.
- A dedicated structural cookie recipe may generate `NewCookie` only when every attribute is
  resolved, max-age fits the target integer domain, SameSite is a target enum value, Partitioned is
  false, and runtime tests prove the resulting header contract—including default version and
  attribute formatting.
- Refuse Partitioned, unresolved/free-form SameSite, overflowing/dynamic duration, custom encoding,
  or code that depends on `ResponseCookie.toString()` formatting unless an explicit raw-header
  serializer policy is selected.

Exact `Set-Cookie` formatting is a wire-level compatibility concern; two object models containing
similar fields are not sufficient evidence. Multiple cookies must remain multiple `Set-Cookie`
values rather than a comma-joined header.

### Cache control

A direct Spring-to-Jakarta `CacheControl` object translation is unsafe. A new Jakarta
`CacheControl` has `no-transform` enabled by default, while a Spring chain such as
`CacheControl.noStore()` represents only the directives selected by that Spring builder. Jakarta's
model also uses integer ages, while Spring accepts `Duration`/long seconds and supports directives
such as `immutable`, `stale-if-error`, and `stale-while-revalidate`. See the
[Spring `CacheControl` API](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/http/CacheControl.html) and
[Jakarta `CacheControl` API](https://jakarta.ee/specifications/restful-ws/3.1/apidocs/jakarta.ws.rs/jakarta/ws/rs/core/cachecontrol).

For exact v0.2 behavior:

- Fully constant, allowlisted Spring chains may be evaluated by the recipe and emitted as the exact
  raw `Cache-Control` header value, with recipe tests pinning directive spelling and order.
- A generated Jakarta `CacheControl` must begin by disabling target `noTransform` unless the source
  explicitly selected it, and must prove every directive and range. Even then, runtime header
  serialization needs a contract test.
- Dynamic chains, extensions, target-unsupported directives, ages outside the target range, and
  custom header post-processing are refusals unless a dedicated raw-header expression generator
  preserves them.

Do not rely on either model's deprecated/string formatting as an undocumented cross-runtime
serialization API.

## Recommended v0.2 implementation boundary

### Canonical automatic set

1. Convert positive, resolved `produces`/`consumes` values while preserving class/method placement,
   and refuse negation or unresolved/composed mappings.
2. Convert only explicitly query-only optional `String` request parameters, or keep query-only as a
   named opt-in if the repository has no machine-readable endpoint contract.
3. Convert optional, single-valued `String` headers when no default is present.
4. Convert whole `HttpHeaders` parameters only for the allowlisted read-only operations above.
5. Convert `ResponseEntity` factories and known 100–599 statuses, non-generic bodies with available
   writers, statically unrollable non-null headers, and known content types.
6. Preserve possibly relative `Location` as a raw header rather than calling target `location`.
7. Convert fully constant allowlisted cache-control chains to raw headers.
8. On any unsupported construct, leave the entire controller unchanged and emit a precise marker
   and data-table row.

### Separately activatable policies

- query-only interpretation of Spring `@RequestParam`;
- `@NotNull` requiredness with status-only error equivalence;
- missing-or-empty normalization for literal `String` defaults;
- source-compatible cookie decoding;
- typed argument `ParamConverter` and invalid-value error mapping;
- status-only `@ResponseStatus`/`ResponseStatusException` migration;
- a chosen error representation for reason-bearing exceptions;
- structurally verified Spring response cookies.

### Canonical refusals for v0.2

- negative media-type expressions and custom content-negotiation/composed mappings without a
  dedicated project scan;
- named-value defaults containing placeholders/expressions, typed empty-value defaults, custom
  converters, primitive requiredness, unnamed all-parameter maps, or ambiguous query/form/multipart
  origin;
- cookie decoding whose source configuration is unknown, Servlet cookie mutation/escape, or
  unsupported response-cookie attributes;
- mutable/escaping whole request headers or unrecognized typed header access;
- reason-bearing status annotations/exceptions without an explicit error policy;
- escaped builders, `.headers(Consumer)`, unresolved `.headers(HttpHeaders)`, generic bodies whose
  type cannot be reified, relative `Location` sent through target `.location`, status outside
  100–599, and dynamic/unsupported cache-control chains.

## Tests

### OpenRewrite recipe tests

Every accepted and refused shape needs an attributed `RewriteTest` case. Tests should cover:

- exact before/after imports, annotation placement, builder order, and generic types;
- explicit source defaults as well as omitted members;
- one refusal reason and data-table row per unsupported construct;
- controller atomicity: one unsupported method prevents partial migration that would alter routing
  or response precedence;
- expressions with side effects to prove evaluation count/order is unchanged;
- method overrides, interface annotations, direct callers, lambdas, and parameter escape;
- a second recipe cycle producing no further changes;
- compilation of every accepted output against the pinned Helidon MP 4.5.x/Jakarta APIs;
- residue assertions showing that accepted target controllers no longer import Spring web/HTTP
  types.

### Differential HTTP contract harness

Run the same requests against a Spring Boot 4/Spring Framework 7 source fixture and the rewritten
Helidon MP 4.5.x fixture. Compare status, ordered multivalue headers where ordering is significant,
content type, and entity bytes or a deliberately normalized semantic representation.

Media-type cases:

- class versus method declarations; one and multiple values; wildcards and parameters;
- missing, matching, wildcard, weighted, and mismatching `Accept` values;
- missing, matching, parameterized, and mismatching `Content-Type` values;
- 406/415 results, competing same-path methods, and actual reader/writer selection.

Request-value cases:

- absent, empty, one, and repeated query/header/cookie values;
- the same name in query and form data, form-only data, and multipart data;
- percent-encoded cookie/query values and distinct `+`, `%2B`, and `%20` inputs;
- required reference, primitive, collection, array, and optional shapes;
- literal defaults and refusal of `${...}`/`#{...}` defaults;
- valid and invalid numeric/custom conversions, checking both status and error entity;
- mixed-case and repeated header names, plus `getFirst` versus comma-joined access.

Status and response cases:

- method-, type-, and exception-level `@ResponseStatus`, with and without reason;
- precedence when a method also returns a status-bearing response;
- `ResponseStatusException` with status, reason, cause, and response headers;
- all accepted `ResponseEntity` factories, null bodies, 204, duplicate headers, and arbitrary known
  100–599 statuses; refusal of 600–999;
- parameterized list/map bodies to verify writer selection and `GenericEntity` generation;
- known content types and both absolute and relative `Location` values;
- multiple `Set-Cookie` values and path/domain/max-age/secure/HTTP-only/SameSite/Partitioned cases;
- `no-cache`, `no-store`, max-age, s-maxage, private/public, must-revalidate, no-transform,
  immutable, and stale directives, explicitly detecting an accidentally added `no-transform`.

Helidon runtime tests are not a substitute for the static boundary. They pin implementation details
that the specifications intentionally leave open—especially validation bodies, error-page shape,
header serialization, and provider availability—so a future Helidon upgrade reveals drift rather
than silently changing migrated APIs.
