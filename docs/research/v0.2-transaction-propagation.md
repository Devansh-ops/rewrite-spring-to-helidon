# Spring Framework 7 transaction semantics versus Jakarta Transactions 2.0

**Status:** Design input for the v0.2 transaction recipe
**Scope:** `org.springframework.transaction.annotation.Transactional` in Spring Framework 7.0.x to
`jakarta.transaction.Transactional` from Jakarta Transactions 2.0, for imperative CDI-managed
application code

## Conclusion

OpenRewrite can automate most propagation conversion, but matching enum names is not by itself a
proof of equivalent behavior.

- `REQUIRED`, `REQUIRES_NEW`, `MANDATORY`, `NOT_SUPPORTED`, and `NEVER` have direct
  transaction-context mappings.
- `SUPPORTS` has the same active-transaction decision, but Spring can also create a resource
  synchronization scope when no real transaction exists. That extra behavior has no Jakarta
  `TxType` contract, so the canonical recipe should refuse it unless a stronger precondition is
  established; a clearly named opt-in leaf recipe may map it.
- `NESTED` has no `TxType` equivalent and must be refused. `REQUIRES_NEW` is not a substitute.
- Non-default isolation, timeout, read-only, labels, or transaction-manager selection have no
  member on Jakarta `@Transactional` and must not be dropped.
- Type-based rollback rules can be mapped only after checking their inheritance relationships.
  Spring chooses the closest matching positive or negative rule; Jakarta always gives
  `dontRollbackOn` precedence when both match.
- String-pattern rollback rules have no Jakarta equivalent and must be refused.
- Spring Framework 7 can change rollback defaults globally. The effective global policy must be
  discovered before rewriting any individual annotation.
- Spring explicitly rolls back on `Error` by default, while the Jakarta Transactions 2.0 text
  expressly names `RuntimeException` but does not expressly state the result for `Error`. Exact
  preservation should therefore add `Error.class` to `rollbackOn`, or be guarded by a target-runtime
  conformance test that proves and documents the same behavior.

These are bounded migrations, not reasons to leave all propagation conversion manual.

## Annotation defaults and available members

Spring's annotation is converted into a `RuleBasedTransactionAttribute`. Its defaults and
Spring-only members are defined in the
[`@Transactional` API](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/transaction/annotation/Transactional.html).
Jakarta Transactions defines only `value`, `rollbackOn`, and `dontRollbackOn`; all three have
defaults in the
[Jakarta API source](https://github.com/jakartaee/transactions/blob/2.0.0/api/src/main/java/jakarta/transaction/Transactional.java#L62-L158).

| Concern | Spring Framework 7 default | Jakarta Transactions 2.0 default | Recipe consequence |
| --- | --- | --- | --- |
| Propagation | `Propagation.REQUIRED` | `TxType.REQUIRED` | Direct default mapping |
| Isolation | `Isolation.DEFAULT` | No annotation member | Accept only the effective default |
| Timeout | `-1`, or `timeoutString = ""` | No annotation member | Accept only the effective defaults |
| Read-only | `false` | No annotation member | Accept only `false` |
| Labels | Empty array | No annotation member | Accept only an empty array |
| Manager | Empty `value` / `transactionManager` alias | No annotation member | Accept only empty local values, subject to the project-level manager checks below |
| Rollback types | Empty arrays; normally rollback for `RuntimeException` and `Error`, not checked exceptions | Empty arrays; the specification states rollback for `RuntimeException`, not checked exceptions | Preserve `Error` explicitly unless conformance is proven |
| Placement | Type or method; class-level is inherited and method metadata overrides class metadata | Type or method; class-level is inherited and method metadata overrides class metadata | Structurally aligned, but only CDI business-method interception is valid at the target |

An explicitly written source default is still a default. For example,
`isolation = Isolation.DEFAULT`, `timeout = -1`, `timeoutString = ""`, `readOnly = false`,
`label = {}`, and `transactionManager = ""` may be normalized away when their constant values are
resolved. Unresolved values must be refused rather than guessed.

## Propagation mapping

The Spring definitions are in the
[`Propagation` Javadoc](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/transaction/annotation/Propagation.html),
and the target behavior is normative in
[Jakarta Transactions section 3.7](https://jakarta.ee/specifications/transactions/2.0/jakarta-transactions-spec-2.0.html#transactional-annotation).

| Spring propagation | Jakarta `TxType` | Mapping status | Exact boundary and caveat |
| --- | --- | --- | --- |
| `REQUIRED` | `REQUIRED` | Automatic | Join an existing transaction, otherwise create one. Both annotations default to this. |
| `REQUIRES_NEW` | `REQUIRES_NEW` | Automatic | Suspend an existing transaction and run in a new one. Spring notes that suspension depends on its transaction manager; Jakarta requires the interceptor to suspend and resume. |
| `MANDATORY` | `MANDATORY` | Automatic with residue check | Require an existing transaction. Failure exception classes differ: Jakarta requires `TransactionalException` with `TransactionRequiredException`; source code catching Spring's transaction-state exception remains residue. |
| `SUPPORTS` | `SUPPORTS` | Architecture-dependent | Both join an existing transaction and otherwise execute without one. Spring may nevertheless establish transaction synchronization and share a JDBC connection or persistence session across the scope. Jakarta specifies only transaction-context behavior. |
| `NOT_SUPPORTED` | `NOT_SUPPORTED` | Automatic | Suspend an existing transaction and run without one. As with `REQUIRES_NEW`, Spring support for actual suspension is manager-dependent while Jakarta requires it. |
| `NEVER` | `NEVER` | Automatic with residue check | Run without a transaction and reject an existing one. Jakarta requires `TransactionalException` with `InvalidTransactionException`; code coupled to Spring's exception type must remain visible. |
| `NESTED` | None | Refusal | Spring uses a nested transaction, commonly a savepoint, and behaves like `REQUIRED` if no transaction exists. Spring explicitly says there is no analogous standard transaction attribute. |

`SUPPORTS` is the only same-named value with a documented source-side behavior beyond the target
transaction-context contract. Spring's common platform transaction-manager base defaults to
`SYNCHRONIZATION_ALWAYS` and can create an "empty" transaction scope with synchronization even when
there is no backend transaction; see the
[implementation](https://github.com/spring-projects/spring-framework/blob/v7.0.8/spring-tx/src/main/java/org/springframework/transaction/support/AbstractPlatformTransactionManager.java#L130-L136)
and its [no-existing-transaction branch](https://github.com/spring-projects/spring-framework/blob/v7.0.8/spring-tx/src/main/java/org/springframework/transaction/support/AbstractPlatformTransactionManager.java#L392-L419).
A separate opt-in recipe can still implement the literal mapping for teams that have established
that resource synchronization outside a real transaction is irrelevant.

## Spring-only attributes

Jakarta Transactions 2.0 has no declarative equivalents for the following Spring members:

- `isolation` other than `DEFAULT`;
- `timeout` other than `-1`, or non-empty `timeoutString` including property placeholders;
- `readOnly = true`;
- non-empty `label` values;
- non-empty `value` or `transactionManager` manager selection.

Spring states that isolation and timeout apply only when a transaction is newly started, and that
read-only is a hint which a transaction manager may use for optimization or ignore. Labels can be
interpreted by a particular transaction manager. Manager names and qualifiers select among regular
and reactive transaction managers. Those effects are described in the
[Spring annotation API](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/transaction/annotation/Transactional.html#transactionManager()).
Their conditional or provider-specific nature does not make them safe to erase.

Manager selection also exists outside the annotation. Since Spring Framework 6.2, a type-level bean
qualifier can select the transaction manager for an otherwise unqualified transaction. Applications
can additionally use `TransactionManagementConfigurer`, primary beans, XML transaction advice, or
custom transaction infrastructure. A local empty annotation value is therefore necessary but not
sufficient evidence that manager choice is irrelevant.

## Rollback semantics

### Defaults

Spring's documented local default is rollback for `RuntimeException` and `Error`, but not checked
exceptions. Jakarta Transactions 2.0 states rollback for `RuntimeException` and its subclasses and no
rollback for checked exceptions. The Jakarta API uses raw `Class[]` members, so `Error.class` is a
legal explicit `rollbackOn` value. To make preservation independent of an implementation's reading
of the specification's silence about `Error`, the generated target should include it:

```java
@jakarta.transaction.Transactional(rollbackOn = Error.class)
```

If another mapped rollback type is present, `Error.class` should be included in that array. A mapped
`dontRollbackOn` rule for `Error` or a subtype still takes precedence at the target, as required by
Jakarta Transactions.

### Type-based rules

Spring `rollbackFor` and `noRollbackFor` and Jakarta `rollbackOn` and `dontRollbackOn` all apply a
class rule to subclasses. The difference is conflict resolution:

- Spring selects the closest matching rule in the thrown exception's inheritance hierarchy. Its
  parser adds positive rules before negative rules, and the implementation replaces the winner only
  for a strictly closer match. Consequently, an equal-depth tie selects the positive rollback rule.
  See the [parser order](https://github.com/spring-projects/spring-framework/blob/v7.0.8/spring-tx/src/main/java/org/springframework/transaction/annotation/SpringTransactionAnnotationParser.java#L88-L101)
  and [winner selection](https://github.com/spring-projects/spring-framework/blob/v7.0.8/spring-tx/src/main/java/org/springframework/transaction/interceptor/RuleBasedTransactionAttribute.java#L123-L142).
- Jakarta specifies that `dontRollbackOn` takes precedence whenever both target arrays match, as
  stated in [section 3.7](https://jakarta.ee/specifications/transactions/2.0/jakarta-transactions-spec-2.0.html#transactional-annotation).

For every source positive type `R` and negative type `D`, a direct array mapping is safe only if:

1. the types are unrelated; or
2. `D` is a strict subtype of `R`.

It is unsafe if `R` equals `D` or `R` is a subtype of `D`. In those cases Spring's closer or
equal-first positive rule can choose rollback while Jakarta's matching negative rule must choose no
rollback.

Examples:

| Source rules | Exception | Spring | Direct Jakarta mapping | Decision |
| --- | --- | --- | --- | --- |
| `rollbackFor = Exception`, `noRollbackFor = IOException` | `FileNotFoundException` | No rollback; negative is closer | No rollback | Safe |
| `rollbackFor = IOException`, `noRollbackFor = Exception` | `FileNotFoundException` | Rollback; positive is closer | No rollback; negative always wins | Refuse |
| Same type in both arrays | That type | Rollback; positive parser entry wins the tie | No rollback | Refuse |
| Unrelated positive and negative types | Either family | Only one rule matches | Only one rule matches | Safe |

This validation requires attributed exception types. Missing types are a refusal, not permission to
copy the arrays.

### String-pattern rules

`rollbackForClassName` and `noRollbackForClassName` are not class-name equality checks. Spring
performs substring matching against the thrown exception's fully qualified name, with no wildcard,
and warns that the rule can also match similarly named or nested exception classes. Jakarta has no
string-rule member. Any non-empty pattern array must therefore be refused. Resolving a string to a
currently available class and converting it would narrow the original rule and would not preserve
its behavior.

### Global and programmatic defaults

Spring Framework 7 can set
`@EnableTransactionManagement(rollbackOn = RollbackOn.ALL_EXCEPTIONS)`. That changes the effective
default for both Spring and Jakarta transaction annotations while Spring manages them. Spring also
allows custom defaults through `AnnotationTransactionAttributeSource.addDefaultRollbackRule(...)`.
Transaction-specific rules override those defaults only for matching exceptions; the chosen global
default remains for other exceptions. These behaviors are documented in the
[Spring 7 transaction reference](https://docs.spring.io/spring-framework/reference/7.0/data-access/transaction/declarative/annotations.html#transaction-declarative-attransactional-settings).

Once Spring transaction infrastructure is removed, its global setting no longer affects Jakarta's
interceptor. A scanning recipe must therefore determine the effective source policy before local
annotation conversion:

- `RUNTIME_EXCEPTIONS`: preserve the normal default, including explicit `Error.class` as described
  above.
- `ALL_EXCEPTIONS`: add `Exception.class` and `Error.class` to target `rollbackOn`, then apply the
  same positive/negative hierarchy validation.
- custom default rollback rules, conflicting enablement, XML advice, or unresolved configuration:
  refuse the affected migration scope and report the source of uncertainty.

## Runtime applicability boundaries

Even a perfectly mapped annotation has behavior only if the target runtime intercepts the same work.

- Jakarta `@Transactional` is a CDI interceptor binding on managed beans. It intercepts business
  method invocations, not lifecycle events; lifecycle transaction context is unspecified. The
  [Jakarta specification](https://jakarta.ee/specifications/transactions/2.0/jakarta-transactions-spec-2.0.html#transactional-annotation)
  also forbids calls to `UserTransaction` inside `REQUIRED`, `REQUIRES_NEW`, `MANDATORY`, or
  `SUPPORTS` annotated scopes.
- Spring can use an imperative `PlatformTransactionManager` or a `ReactiveTransactionManager`.
  Reactive transactions use Reactor context and require a reactive pipeline. A Jakarta CDI business
  interceptor around the method invocation does not preserve that pipeline-scoped behavior. The
  distinction is explicit in the
  [Spring annotation API](https://docs.spring.io/spring-framework/docs/7.0.x/javadoc-api/org/springframework/transaction/annotation/Transactional.html).
- Spring's default proxy mode intercepts external calls only; AspectJ mode also intercepts local
  calls. The [Spring reference](https://docs.spring.io/spring-framework/reference/7.0/data-access/transaction/declarative/annotations.html#transaction-declarative-annotations-method-visibility)
  documents both modes. AspectJ transaction enablement must be refused unless an equivalent target
  invocation model has been selected.
- Spring transactional test support has test-managed rollback behavior and is not a CDI business
  transaction. Test classes must not be converted by this production recipe.

Accordingly, the canonical recipe should continue to require an interceptable CDI bean and should
also refuse lifecycle methods, reactive return types or reactive manager selection, AspectJ
transaction mode, transactional test contexts, and affected scopes that call `UserTransaction`.

## Recommended v0.2 recipe algorithm

Use a scanning recipe so local edits depend on source-set or module-wide evidence.

1. Inventory transaction enablement, global rollback mode, programmatic default rules, XML advice,
   transaction manager declarations and qualifiers, reactive transaction usage, AspectJ mode, and
   transactional test support.
2. Preflight each effective class hierarchy as one atomic unit. A supported class-level annotation
   must not be converted while an overriding unsupported Spring method annotation is left inert, or
   the new class-level Jakarta annotation would unexpectedly govern that method.
3. Require attributed source types, a CDI bean-defining annotation, and an interceptable imperative
   business method.
4. Normalize explicit source defaults. Refuse every effective non-default Spring-only member.
5. Map the five automatic propagation values. Refuse `NESTED`; keep `SUPPORTS` in a separately
   activatable recipe unless its extra source behavior is proven irrelevant.
6. Refuse non-empty string rollback patterns. For class rules, perform the positive-versus-negative
   hierarchy check before copying them.
7. Materialize the effective global rollback policy in target annotation members, including the
   explicit `Error.class` preservation rule.
8. On any failed precondition, leave the complete Spring annotation unchanged and emit a precise
   refusal marker and data-table row. Do not partially rewrite its propagation or rollback members.
9. Clean imports only after a successful replacement and verify a second recipe cycle is a no-op.

## Required tests

### Source transformation acceptance

1. Bare Spring `@Transactional` becomes Jakarta `@Transactional` with explicit Spring-compatible
   `Error` rollback behavior.
2. Explicit `REQUIRED`, `REQUIRES_NEW`, `MANDATORY`, `NOT_SUPPORTED`, and `NEVER` map to the
   corresponding `TxType`.
3. Propagation combines correctly with one or both safe type-based rollback arrays.
4. Explicit default values (`DEFAULT`, `-1`, empty string/array, `false`, empty manager) are accepted
   and removed.
5. A class-level annotation and a supported method-level override retain their override structure.
6. Fully qualified names, ordinary imports, and static enum imports produce valid target imports.
7. An already-Jakarta annotation is unchanged, and a second recipe cycle makes no changes.

### Refusals

1. `NESTED` is preserved with a specific no-equivalent refusal.
2. `SUPPORTS` is preserved by the canonical recipe and converted only by its opt-in leaf recipe.
3. Every non-default isolation level is refused.
4. Positive `timeout`, non-empty `timeoutString`, `readOnly = true`, non-empty labels, and non-empty
   manager selection through either alias are refused independently.
5. Reactive annotated methods and type-level annotations governing reactive methods are refused.
6. Lifecycle methods, transactional tests, interface-only placements, and non-interceptable CDI
   targets are refused.
7. An affected transactional scope that calls `UserTransaction` is refused.
8. AspectJ transaction mode, unresolved annotation constants, custom transaction attribute sources,
   and unresolved global rollback configuration refuse the affected scope.
9. Refusal leaves annotation arguments and imports intact and adds only the diagnostic marker/data.

### Rollback-rule interactions

1. Disjoint positive and negative exception families map.
2. A negative subtype of a positive type maps and retains no-rollback behavior for the subtype.
3. A positive subtype of a negative type is refused.
4. The same class in both arrays is refused.
5. Missing type attribution is refused.
6. Any non-empty `rollbackForClassName` or `noRollbackForClassName` is refused, including a fully
   qualified string that happens to resolve to a class.
7. `RUNTIME_EXCEPTIONS` and `ALL_EXCEPTIONS` global modes materialize different target arrays.
8. A custom default rollback rule blocks local conversion until an explicit target policy exists.
9. Runtime conformance tests cover checked exceptions, runtime exceptions, `Error`, and mapped
   positive/negative subtype combinations.

### Propagation runtime conformance

Source-rewrite assertions cannot prove transaction semantics. A target-runtime fixture should also
verify:

1. `REQUIRED` joins an outer transaction and creates one without an outer transaction.
2. `REQUIRES_NEW` commits independently and resumes the outer transaction.
3. `MANDATORY` rejects a call without a transaction and joins one when present.
4. `NOT_SUPPORTED` suspends and later resumes the outer transaction.
5. `NEVER` rejects a call with a transaction and runs without one otherwise.
6. The opt-in `SUPPORTS` mapping joins a transaction when present and runs without one otherwise,
   with the accepted lack of Spring's non-transactional resource-synchronization guarantee recorded.

## Non-goals

This work does not choose a transaction provider, datasource, persistence-unit policy, isolation
policy, timeout policy, manager-routing strategy, or reactive replacement. OpenRewrite can inventory
and scaffold those concerns, but they require an architecture-dependent recipe with explicit target
options rather than silent defaults in the canonical migration.
