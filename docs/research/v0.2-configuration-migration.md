# v0.2 configuration migration research

**Status:** planning input
**Target baseline:** Spring Framework 7 / Spring Boot 4 to Helidon MP 4.5.x,
MicroProfile Config 3.1, and Java 21

## Executive conclusion

OpenRewrite can automate substantially more configuration migration than the current recipe does,
but direct annotation substitution is not enough. Spring and MicroProfile differ in missing-value
behavior, conversion rules, key lookup, source precedence, profiles, and validation. The canonical
migration should therefore remain fail-closed and use a project-wide configuration index before it
changes Java and resource files together.

The safe v0.2 tranche is:

1. Add a read-only configuration assessment that inventories injection points, configuration
   property classes, resource files, profiles, custom converters, source-loading features, and
   secret-bearing keys without recording values.
2. Add a bounded migration for flat, mutable JavaBean-style `@ConfigurationProperties` classes
   only when every field, injection site, default, key, and converter is representable.
3. Copy the portable subset of a simple classpath `application.properties` into
   `META-INF/microprofile-config.properties`, merge only collision-free entries, and retain the
   Spring file until the migration finalizer proves it is unused.
4. Correct the existing `@Value` scalar boundary, then add only type mappings whose complete
   conversion contract is proven. Enum, duration, period, optional, collection, and empty-default
   cases should remain refusals in the canonical recipe until either a compatibility
   converter/producer is generated or an explicit option accepts a narrower target contract.

The last point is important: MicroProfile Config supports all these shapes, so they are
automatable. They are not all behavior-preserving as a bare `@Value` to `@ConfigProperty` rewrite.

## Authoritative baseline

Helidon MP 4.5.x implements MicroProfile Config 3.1 and Jakarta Bean Validation 3.0, among its
MicroProfile 6.1/Jakarta APIs ([Helidon MP specifications](https://helidon.io/docs/v4/mp/specifications)).
Its default configuration sources are system properties, environment variables, and
`META-INF/microprofile-config.properties` ([Helidon MP Config](https://helidon.io/docs/v4/mp/config)).

Spring Boot supports a much broader, ordered configuration model: packaged and external
`application.properties`/YAML, profile variants, environment variables, system properties, inline
JSON, command-line arguments, test sources, imports, config trees, and custom sources. Later sources
in its documented order override earlier ones
([Spring Boot externalized configuration](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html)).

MicroProfile Config instead assigns each source an ordinal. Its required defaults are system
properties at 400, environment variables at 300, and each classpath
`META-INF/microprofile-config.properties` at 100. Higher ordinals win
([MicroProfile Config 3.1, ConfigSources](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#configsources)).

These models overlap, but they are not interchangeable.

## Classification

| Area | Safe generic mapping | Option-driven or generated compatibility | Canonical refusal |
| --- | --- | --- | --- |
| Simple classpath properties | Copy keys consumed by migrated code into the MP resource; preserve comments and escaping; merge only without conflicts | Select explicit source ordinals or create Helidon meta-configuration | Imports, config trees, remote/custom sources, duplicate conflicts, or unproven precedence |
| Server basics | Keep `server.port`; map `server.address` to `server.host` | Other server behavior with a selected Helidon policy | Unmapped `server.*` keys |
| Flat `@ConfigurationProperties` | Mutable zero-arg JavaBean, flat supported fields, explicit defaults, all injection sites known | Generate a CDI producer/binder and validation hook | Records, constructor binding, nested objects, maps, custom bind handlers, inaccessible setters, conditional registration |
| `@Value` enum | None as a whole-domain bare annotation substitution | Generate a per-enum MP converter or accept exact identifier-only input and normalize managed values | Custom converters, aliases, case/format leniency, unknown external contract |
| `@Value` duration/period | None unless source and target conversion are both proven and values are ISO-8601 | Generate Spring-compatible MP converters, or normalize all managed values with an explicit external-contract decision | Per-property units, custom conversion, or unknown external values |
| `@Value` arrays/lists/sets | A characterized non-empty comma subset can be offered as an opt-in first | Generate a compatibility producer/parser | Empty elements, custom delimiters, SpEL splitting, maps, nested collections |
| `@Value` optional | None as a direct generic rewrite | Generate programmatic lookup with an explicitly selected missing/empty policy | Bare annotation substitution |
| Empty default | None with `@ConfigProperty.defaultValue` | Generate `Config#getOptionalValue(...).orElse("")` or an equivalent producer | `defaultValue = ""`, which MP ignores |
| Profiles | One literal profile and classpath-only profile files, if selected explicitly | Generate profile-aware custom sources for a declared ordered profile policy | Multiple active profiles, groups/includes, activation documents, location groups |
| Validation | Preserve Jakarta constraints as metadata | Generate explicit startup validation and add the Helidon validation dependency | Assuming `@Validated` automatically retains Spring binding-time behavior; custom Spring `Validator` beans |
| Secrets | Preserve references; report keys only; never copy values into Java or reports | Generate a declared external/config-tree source or adopt target encryption with supplied policy | Inventing encryption keys, emitting plaintext defaults, or silently changing secret sources |

## Semantic findings

### 1. `@Value` is extensible, not a fixed conversion contract

Spring resolves `@Value` through a bean post-processor and a `ConversionService`; applications can
replace that service. Spring's documented built-ins cover simple conversions and comma-separated
`String[]`, while SpEL and nested/default placeholders add another language layer
([Spring Framework `@Value`](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/value-annotations.html)).

MicroProfile Config has a fixed portable core plus service-loaded converters. It provides primitive
and wrapper converters, array conversion, CDI injection for arrays, `List`, and `Set`, and automatic
conversion when a type exposes `of(String)`, `valueOf(String)`, `parse(CharSequence)`, or a public
`String` constructor
([MicroProfile Config 3.1 converters](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#converters)).

Therefore a scanner must detect at least:

- a bean named `conversionService`;
- `@ConfigurationPropertiesBinding` converters;
- custom property editors or bind handlers;
- SpEL, nested placeholders, and non-literal annotation arguments; and
- service-loaded target converters already present in the module.

Any detected custom source converter makes a same-type annotation substitution unproven unless the
recipe also migrates that converter.

### 2. Enums are supported but not generally equivalent

Spring Framework's standard string-to-enum conversion trims the input before calling
`Enum.valueOf`, while Spring Boot's configuration-properties conversion can be more lenient. MP's
portable automatic converter invokes a matching `valueOf(String)` without specifying trimming or
Spring's leniency
([Spring conversion reference](https://docs.spring.io/spring-framework/reference/core/validation/convert.html),
[MP automatic converters](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#_automatic_converters)).

A direct mapping is safe only for an explicitly closed configuration contract whose possible values
are exact enum identifiers. Since configuration is normally externally supplied, the canonical
recipe should either refuse or generate a converter for that enum which preserves the accepted
source spellings. The latter is mechanically feasible with a scanning recipe plus
`META-INF/services/org.eclipse.microprofile.config.spi.Converter`.

### 3. Duration and period support intersects at ISO-8601

Spring Boot configuration binding accepts ISO-8601, numeric values with a default or annotated
unit, and compact forms such as `10s` for `Duration` and `1y3d` for `Period`
([Spring Boot duration conversion](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.conversion.duration),
[Spring Boot period conversion](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.conversion.period)).
MP can automatically use `Duration.parse(CharSequence)` and `Period.parse(CharSequence)`, which
provides the ISO-8601 intersection, but it does not standardize Spring's compact or per-injection
unit rules.

For `@Value`, the source behavior may also come from an application-defined `ConversionService`, so
the Boot binder rules must not be assumed merely because the application uses Boot.

Two later recipes are realistic:

- normalize literal defaults and repository-managed property values to ISO-8601, while exporting
  every affected key as an external configuration contract change; or
- generate and register target `Converter<Duration>` and `Converter<Period>` implementations which
  accept the supported Spring formats.

`@DurationUnit` and `@PeriodUnit` are property-specific, whereas an MP converter is type-wide.
Members using non-default units therefore need value normalization or a property-specific producer,
not a global converter alone.

### 4. Optional and empty values have materially different behavior

MP explicitly supports injecting `Optional<T>` and treats a missing or erased property as empty.
It also treats an empty value as property deletion
([MP injection examples](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#_simple_dependency_injection_example),
[MP property removal](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#_remove_config_properties)).

Spring Boot explicitly warns that a missing `Optional` member in `@ConfigurationProperties` is
bound as `null`, not `Optional.empty()`
([Spring Boot type-safe configuration](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.constructor-binding)).
For `@Value`, placeholder resolution and conversion are separate, so an `Optional` target does not
by itself define an equivalent missing-property policy.

An empty `@Value` default is especially clear-cut. Spring can inject `""` from `${key:}`, but MP
states that an empty `@ConfigProperty.defaultValue` is ignored, exactly as if no default were set
([`ConfigProperty` Javadoc](https://download.eclipse.org/microprofile/microprofile-config-3.1/apidocs/org/eclipse/microprofile/config/inject/ConfigProperty.html#defaultValue())).

These cases are automatable only by changing the access pattern, for example to
`Config#getOptionalValue` plus an explicit `orElse` policy, or by generating a producer. A direct
annotation rewrite must remain a refusal.

### 5. Lists overlap, but edge cases differ

Spring documents automatic comma conversion for `String[]`; other collection behavior can depend
on its conversion service. MP standardizes comma-delimited arrays and CDI injection into arrays,
`List`, and `Set`, using backslash as the comma escape character
([Spring `@Value`](https://docs.spring.io/spring-framework/reference/core/beans/annotation-config/value-annotations.html),
[MP array converters](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#_array_converters)).

MP also assigns special deletion behavior to empty strings and to some comma-only inputs. A bounded
mapping must characterize whitespace, escaped commas, empty elements, duplicate set entries,
element conversion, defaults, and missing values. Until that matrix is tested against both
runtimes, collections belong in an opt-in recipe or a generated compatibility producer.

### 6. Even boolean conversion needs a compatibility check

MP's standard boolean converter recognizes a defined true set and treats every other value as
`false`. Spring's standard converter recognizes explicit true and false sets and rejects an
unrecognized non-empty token
([MP built-in converters](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#_built_in_converters),
[Spring Framework `StringToBooleanConverter` source](https://github.com/spring-projects/spring-framework/blob/7.0.x/spring-core/src/main/java/org/springframework/core/convert/support/StringToBooleanConverter.java)).

Consequently, malformed external input can change from startup failure to a silent `false`. The
existing scalar mapping should gain a regression test and either a refusal boundary or a generated
strict target converter. Numeric and character conversions should receive the same whole-domain
characterization rather than being assumed equivalent from successful happy-path tests.

### 6.1. Audit of the existing scalar boundary

The current direct annotation rewrite accepts `String`; primitive and boxed `boolean`, `byte`,
`short`, `int`, `long`, `float`, and `double`; and rejects `char`/`Character`. That entire accepted
set needs a narrower claim:

| Current target types | Status | Counterexample or unproven condition |
| --- | --- | --- |
| `String` | Proven non-equivalent | Spring can inject an explicitly configured empty string; MP treats an empty value as deletion. |
| `boolean` / `Boolean` | Proven non-equivalent | MP accepts `y` as true and maps every other non-true value to false; Spring accepts a smaller true/false vocabulary and rejects unknown tokens. Spring also trims input while Helidon's built-in MP converter does not. |
| `byte` / `Byte`, `short` / `Short`, `int` / `Integer`, `long` / `Long` | Proven non-equivalent | Spring removes whitespace and accepts hexadecimal prefixes through `NumberUtils`; Helidon 4.5.x uses the corresponding JDK decimal `parseXxx` functions. |
| `float` / `Float`, `double` / `Double` | Proven non-equivalent | Spring removes all whitespace before parsing; Helidon 4.5.x delegates to the corresponding JDK `parseXxx` function without that normalization. |
| Every boxed scalar | Proven non-equivalent for empty input | Spring's standard scalar converters return `null` for the empty string, while MP erases the property and treats a required injection point as unsatisfied. |
| Every accepted type | Unproven when conversion is customized | A Spring `conversionService` bean can replace source conversion, and an MP service-loaded converter can replace target conversion. |

Spring documents the whitespace normalization and hexadecimal behavior of `NumberUtils`
([Spring Framework `NumberUtils`](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/util/NumberUtils.html));
the MP specification defines empty values, the minimum numeric converter contract, and converter
overrides
([MP converter contract](https://download.eclipse.org/microprofile/microprofile-config-3.1/apidocs/org/eclipse/microprofile/config/spi/Converter.html)).
Helidon 4.5.x's built-ins delegate numeric values to the JDK parsers and implement MP's boolean true
set
([Helidon `ConfigMappers` source](https://github.com/helidon-io/helidon/blob/4.5.3/config/config/src/main/java/io/helidon/config/ConfigMappers.java)).

There are two defensible release boundaries:

- **Strict interpretation of the fail-closed ADR:** the canonical recipe refuses every bare scalar
  rewrite until it either generates Spring-compatible lookup/conversion code or the user selects a
  separately named bounded recipe that declares a non-empty, portable lexical input contract.
- **Smallest urgent correction:** remove primitive and boxed boolean from the direct rewrite now,
  because an invalid source value can become a successful but wrong target value. This prevents the
  silent regression but does **not** make the remaining scalar set whole-domain equivalent; String,
  numeric whitespace/hexadecimal input, empty values, and custom converters must remain tracked
  correctness work.

If the bounded path is retained, its implementation should use explicit primitive/type allowlists
rather than accepting every primitive except a denylist. Its tests must cover every listed type,
and the CDI stereotype preflights must share the same predicate so an unsupported `@Value` member
cannot leave a half-migrated bean.

### 7. Flat `@ConfigurationProperties` is feasible, but must be cross-file

Spring Boot supports mutable JavaBeans, constructor-bound classes and records, relaxed names,
nested structures, lists/maps, field defaults, custom conversion, and validation
([Spring Boot type-safe configuration](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.typesafe-configuration-properties)).

MicroProfile's `@ConfigProperties` supports a prefixed CDI property bean whose fields map to
properties, including private fields, and allows `@ConfigProperty` to override a field's key. The
class should have a zero-argument constructor, and missing required or unconvertible fields cause
deployment errors
([MP aggregate properties](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#_aggregate_related_properties_into_a_cdi_bean)).

A bounded direct mapping can handle a class only when all of these are true:

- it is a non-record Java class with an accessible zero-argument constructor;
- it has only flat, non-static scalar fields in the supported conversion intersection;
- every missing value has a representable explicit default, or a generated binder preserves the
  existing Java field default;
- every Boot relaxed key is made explicit with `@ConfigProperty(name = "...")`;
- every injection site can be found and receives the required MP qualifier;
- no `@Bean` factory, conditional enablement, programmatic lookup, bind handler, or custom converter
  controls its construction; and
- the class is migrated atomically: one unsupported member refuses the entire class.

There are two implementation strategies:

1. **Direct MP property bean.** Replace the type annotation, add a CDI scope such as `@Dependent`,
   add explicit field key/default annotations, and update every injection point. This is compact but
   inherits MP's missing-value and conversion behavior.
2. **Generated CDI producer.** Retain the POJO, instantiate it through its zero-arg constructor,
   use `Config#getOptionalValue`/`getOptionalValues`, call setters only for present properties, then
   validate and produce it. This preserves Spring's field-initializer and missing-value behavior for
   a larger flat subset, at the cost of generated code.

The producer strategy is the safer generalized path for nullable fields and nontrivial defaults.
It should still refuse inaccessible setters, side-effecting setters, overloaded setters, and custom
binding infrastructure.

### 8. Relaxed keys and environment aliases require an explicit contract

Spring Boot accepts camel, kebab, and underscore forms for `@ConfigurationProperties`; its
recommended environment form removes dashes and replaces dots with underscores. MP searches an
exact environment name, a form replacing every non-alphanumeric character with `_`, and an
upper-case version of that form
([Spring relaxed binding](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.relaxed-binding),
[MP environment mapping](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#_environment_variables_mapping_rules)).

For a key containing hyphens, the operational environment variable names can therefore differ.
The recipe should:

- choose one exact target key per injection point;
- update repository-managed property files and deployment manifests when present;
- export old and new environment aliases as data-table columns, never values; and
- refuse to claim equivalence when external deployment configuration is outside the scan.

A later compatibility `ConfigSource` can alias old environment names to target keys, but that is an
architecture-dependent migration and must define conflict precedence.

### 9. Resource locations and precedence are the largest file-level boundary

Spring's classpath root `application.properties` is not an MP default source. Helidon MP uses
`META-INF/microprofile-config.properties`; additional file, URL, YAML, map, and classpath sources can
be configured through its APIs or meta-configuration
([Helidon MP Config](https://helidon.io/docs/v4/mp/config),
[Helidon advanced configuration](https://helidon.io/docs/v4/mp/config/advanced-configuration)).

The canonical file recipe should support only a closed simple case:

- one classpath `application.properties` per module;
- no `spring.config.import`, `@PropertySource`, multi-document separator, YAML peer, custom basename,
  wildcard location, inline JSON, or config tree;
- no conflicting target key already present;
- only keys used by migrated application code or in an approved target mapping table; and
- no literal secret-bearing entry copied into a second file.

The recipe should generate or merge the MP resource, but keep the Spring resource until the
migration finalizer proves no Spring configuration consumer remains. This supports incremental
migration and makes the operation idempotent.

The first approved target mapping table can remain intentionally small:

| Spring Boot key | Target key | Rule |
| --- | --- | --- |
| `server.port` | `server.port` | Preserve value; both products use the key for the HTTP listener port. |
| `server.address` | `server.host` | Rename a scalar bind address/host only; refuse expressions or multi-listener policy. |

Spring Boot documents `server.address` and `server.port`
([Boot application properties](https://docs.spring.io/spring-boot/4.0/appendix/application-properties/index.html#appendix.application-properties.server));
Helidon documents `server.host` and `server.port`
([Helidon MP server](https://helidon.io/docs/v4/mp/server)). Other framework keys need their own
semantic mapping and tests rather than being copied as inert target configuration.

### 10. Profiles are only narrowly portable

Spring supports multiple active profiles and applies a last-wins strategy across profile order and
location groups. It also supports default profiles, imports, profile groups, includes, and
document-level activation
([Spring profile-specific files](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.files.profile-specific)).

MP standardizes one `mp.config.profile`, `%profile.key` properties, and a matching
`META-INF/microprofile-config-<profile>.properties` layered over the base file
([MP Config profiles](https://download.eclipse.org/microprofile/microprofile-config-3.1/microprofile-config-spec-3.1.html#config-profile)).

An opt-in bounded mapping may convert exactly one literal `spring.profiles.active` value and its
classpath files. Multiple profiles or any activation/import feature must be refused unless a custom
source is generated from an explicit ordered policy.

### 11. Validation is available but not automatically attached to config binding

Spring validates an `@ConfigurationProperties` object at binding time when it is annotated with
`@Validated`, including Jakarta constraints and nested `@Valid`; it can also use a specially named
custom Spring `Validator`
([Spring Boot validation](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.validation)).

Helidon supports Jakarta Bean Validation for ordinary application beans, but that does not make a
bare MP property-bean rewrite equivalent to Spring's binding-time validation
([Helidon Bean Validation](https://helidon.io/docs/v4/mp/beanvalidation)).

For standard Jakarta constraints, an opt-in generated producer can call `Validator#validate` after
binding and throw `ConstraintViolationException` before exposing the bean. It must carry validation
groups and add the target validation dependency. Custom Spring validators, bind handlers, and
validation side effects remain refusals.

### 12. Secret handling must avoid new disclosure

Spring supports mounted config trees, including common container-secret layouts, while Spring Boot
does not itself encrypt property values
([Spring config trees](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.files.configtree),
[Spring property encryption boundary](https://docs.spring.io/spring-boot/4.0/reference/features/external-config.html#features.external-config.encrypting)).
Helidon offers config-source extensions and an encryption filter, but using target encryption needs
a master-key and operational policy
([Helidon configuration secrets](https://helidon.io/docs/v4/mp/config#_encryption)).

The recipe must follow these rules:

- never place a property value in a marker, log message, exception, or data table;
- classify likely secret keys by name only and allow explicit additional patterns;
- never move a literal secret into Java source or an annotation default;
- do not manufacture `${CLEAR=...}`, encrypted payloads, or master keys;
- preserve already-external placeholder references only when their target lookup is compatible; and
- refuse source migration for `configtree:`, vault/plugin sources, or literal secret-bearing entries
  until a target secret-source policy is selected.

## Recommended recipe design

Use one scanning recipe to build a module-level `ConfigurationContractIndex` containing only
metadata:

- property key and canonical target key;
- Java consumer and target type;
- source resource path and source kind;
- default kind, but not a secret value;
- converter provenance;
- profile/source precedence features;
- target support classification and refusal reason; and
- old/new environment aliases.

Do not store property values in exported tables. Values can be inspected transiently by visitors to
validate or normalize non-secret literals, but secret-like values must not leave the source tree.

Suggested recipe split:

- `AssessSpringConfiguration` — read-only inventory and data tables;
- `MigrateFlatConfigurationProperties` — atomic bounded JavaBean migration;
- `CopyPortableApplicationProperties` — collision-safe target resource generation;
- `MigrateSingleSpringProfile` — separately activated single-profile mapping;
- `GenerateSpringCompatibleConfigConverters` — later opt-in enum/duration/period support;
- `GenerateConfigLookupProducers` — later opt-in optional, empty-default, list, and nullable-bean
  support; and
- `FinalizeSpringConfigurationRemoval` — delete old resources only after residue gates pass.

## Proposed tests

### Rewrite-level tests

1. **Atomic flat bean:** migrate a zero-arg JavaBean with literal defaults and supported scalar
   fields; update all constructor/field injection sites; run twice and assert idempotence.
2. **Flat bean refusals:** one test each for a record, constructor binding, nested object, map,
   inaccessible or overloaded setter, static/final field, custom converter, conditional enablement,
   programmatic lookup, `ignoreUnknownFields = false`, and `ignoreInvalidFields = true`.
3. **Missing values:** prove field initializer, primitive default, nullable reference, wrapper, and
   optional behavior. Refuse the class when the selected strategy cannot preserve one member.
4. **Enum:** exact identifier succeeds only under its declared boundary; lower case, hyphenated,
   whitespace-padded, aliased, and custom-converter inputs refuse or require the compatibility leaf.
5. **Duration/period:** ISO values succeed in the bounded path; compact, numeric, annotated-unit,
   empty, malformed, and custom-converter values refuse. Test generated converters separately.
6. **Collections:** characterize missing, empty, comma-only, whitespace, escaped comma, empty
   element, duplicates, numeric element failure, defaults, arrays, lists, and sets.
7. **Optional/empty defaults:** canonical recipe emits a refusal and leaves source unchanged;
   producer recipe generates the chosen `orElse` behavior without changing unrelated members.
8. **Boolean regression:** `true`/`false` remain equivalent; an invalid token must not silently
   become `false` if Spring would fail.
9. **Property resource:** copy a simple file while preserving comments, escapes, continuation lines,
   and deterministic ordering; merge idempotently; refuse conflicting duplicate keys.
10. **Known keys:** preserve `server.port`, rename `server.address` to `server.host`, and refuse an
    expression or collision.
11. **Profiles/sources:** support one explicitly enabled classpath profile; refuse multiple profiles,
    groups, includes, imports, config trees, YAML, multi-document files, and custom locations.
12. **Secrets:** verify secret-like values never appear in markers, exceptions, serialized tables,
    snapshots, or generated Java; the row contains only the key and refusal reason.

### Runtime equivalence tests

Recipe snapshots alone cannot prove configuration behavior. Add small Spring Boot 4 and Helidon MP
4.5.x fixtures and run the same value matrix against both:

- classpath property, environment override, and system-property override;
- absent, explicit empty, defaulted, and malformed values;
- exact and noncanonical enum values;
- every supported duration/period syntax;
- collection escaping and empty elements;
- one profile-specific override; and
- standard Bean Validation failure at startup.

For each supported case, assert the same resulting Java value or the same startup-failure class of
outcome. A mapping is canonical only after this differential suite passes. Also compile the rewritten
fixture with Java 21 and the target dependency set, then run the recipe a second time with no diff.

## Deferred but automatable follow-up issues

The following should become GitHub issues even if they do not fit v0.2:

1. Generate strict boolean conversion or narrow the existing boolean migration boundary.
2. Generate per-enum compatibility converters and service registrations.
3. Generate Spring-format `Duration` and `Period` converters, with property-specific unit handling.
4. Generate lookup producers for `${key:}` empty defaults and explicit missing-value policies.
5. Add arrays/list/set migration with a differential delimiter and empty-value suite.
6. Add a producer-based wider flat `@ConfigurationProperties` migration for nullable/defaulted
   fields.
7. Add explicit startup Jakarta validation for migrated configuration beans and groups.
8. Generate declared custom `ConfigSource`/Helidon meta-configuration with ordinal controls.
9. Add YAML and multi-document conversion for a deliberately bounded subset.
10. Add multiple-profile compatibility from an explicitly supplied order policy.
11. Add environment-variable alias compatibility and deployment-manifest rewrites.
12. Add config-tree/secret-source adapters without ever copying secret values.
13. Add a residue-gated configuration finalizer that removes Spring resource files and source-loading
    dependencies only when no Spring consumer remains.

## Bottom line

The current limitations are mostly implementation and safety-boundary decisions, not OpenRewrite
capability limits. Scanning recipes can correlate Java, properties, YAML, Maven/Gradle, service
registrations, and generated files. What OpenRewrite cannot infer is the deployment's external
configuration contract or the operator's desired source, profile, and secret policy. The project can
automate those areas after making the policy explicit; the canonical migration should continue to
refuse when it is not.
